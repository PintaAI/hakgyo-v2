# BlockNote color and theming research

Research date: 2026-09-03
Repository version inspected: `@blocknote/core`, `@blocknote/react`, and `@blocknote/shadcn` 0.53.0

## Executive summary

Hakgyo must bridge **two distinct styling systems** to make BlockNote fully follow the organization theme:

1. `@blocknote/shadcn` UI chrome—toolbars, menus, popovers, buttons, inputs, focus rings, cards, and utility shadows—uses the host application's shadcn/Tailwind semantic tokens such as `--popover`, `--accent`, `--border`, `--ring`, and Tailwind `shadow-*` utilities. BlockNote's ShadCN setup explicitly expects the consuming application to provide those styles and tokens. [Official ShadCN setup](https://www.blocknotejs.org/docs/getting-started/shadcn) and [first-party ShadCN component source at v0.53.0](https://github.com/TypeCellOS/BlockNote/tree/v0.53.0/packages/shadcn/src)
2. The editable document surface and BlockNote's built-in text/background color system use BlockNote-specific variables such as `--bn-colors-editor-background`, `--bn-colors-editor-text`, and the 18 named highlight variables. [Official themes documentation](https://www.blocknotejs.org/docs/react/styling-theming/themes) and [first-party React theme CSS at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/styles.css)

Hakgyo already exposes its shadcn tokens to Tailwind, scans `@blocknote/shadcn`, and now has a scoped `--bn-*` bridge in `apps/web/src/styles/globals.css`. A 0.53.0 source and generated-CSS audit confirms that the current selector matches the actual ShadCN BlockNote roots and has enough specificity to beat BlockNote's packaged light/dark defaults. The reported “still looks the same” behavior is therefore not explained by a wrong `.bn-root` selector or by the package stylesheet loading later. The main cause is visual: Hakgyo's generated dark card/text values are very close to BlockNote's dark defaults, and the material section wrapper and `.bn-editor` both use the same `--card` surface.

## Diagnostic conclusion for Hakgyo

The current bridge is wired correctly, but it does not create a visibly distinct editor surface.

At the time of this audit, the active `hakgyo-system` organization theme resolves to:

| Token | Hakgyo dark value | BlockNote 0.53.0 dark default |
| --- | --- | --- |
| page background | `#0F151A` | not applicable |
| card / BlockNote editor background | `#141C22` | `#1F1F1F` |
| card / BlockNote editor text | `#C8CFD6` | `#CFCFCF` |

The background is technically different and carries a slight blue cast, but both are near-black. The foreground differences per RGB channel are only 7, 0, and 7, so the text is expected to look almost unchanged by eye. These values came from a read-only database query plus `createOrganizationThemePalette()`; no organization data was modified.

There is a second hierarchy issue in `MaterialEditorForm`: the containing `<section>` already uses `bg-card`, while the bridge maps `--bn-colors-editor-background` to that same `--card` token. Consequently, the editor canvas and its surrounding material card intentionally merge into one surface. A stronger visual distinction requires a product-level token decision—such as a dedicated derived editor surface or a larger card/background delta—not a different BlockNote selector.

The inspected material titled `ma` contains no non-default block or inline `textColor` / `backgroundColor` values. Its native paragraph and heading content therefore inherit `.bn-editor`'s themed color. The large lesson UI in the screenshot is a Hakgyo custom block; its React DOM applies app semantic utilities such as `text-foreground`, `text-muted-foreground`, `bg-muted`, and `bg-background` directly. Those declarations intentionally bypass inherited `--bn-colors-editor-text`, although they still follow the organization theme through Hakgyo's own tokens.

### Selector and class propagation

The 0.53.0 ShadCN wrapper merges `bn-shadcn` into the `className` passed to `BlockNoteViewRaw`. The React view then creates the visible container with:

```text
bn-root bn-container <light|dark> bn-shadcn
```

It also copies `bn-root`, the selected scheme, and the same `className` to `editor.portalElement`. Therefore this Hakgyo selector matches both the visible editor root and the default floating-UI portal root:

```css
.bn-root.bn-shadcn[data-color-scheme] { ... }
```

The contenteditable itself is generated by core with `bn-editor` and, while default styles are enabled, `bn-default-styles`. BlockNote's React stylesheet applies the surface exactly as follows:

```css
.bn-editor {
  background-color: var(--bn-colors-editor-background);
  color: var(--bn-colors-editor-text);
}
```

`bn-default-styles` does not set color or background. It does set a fixed Inter font stack, which is why Hakgyo's more-specific `.bn-default-styles` font override is still necessary.

### Cascade and import order

`@blocknote/shadcn/style.css` imports `@blocknote/react/style.css`, and that stylesheet contains the BlockNote theme defaults. In the emitted Next.js development CSS, the relevant specificity is:

| Rule | Specificity |
| --- | --- |
| `.bn-root` package defaults | `0-1-0` |
| `.bn-root[data-color-scheme="dark"]` package defaults | `0-2-0` |
| `.bn-root.bn-shadcn[data-color-scheme]` Hakgyo bridge | `0-3-0` |

No relevant declaration uses `!important`. The Hakgyo bridge therefore wins even when the dynamically imported BlockNote CSS chunk is inserted after the global CSS chunk. Keeping package CSS in one stable global entry before application overrides is still easier to reason about, but changing import order alone will not change the current computed values.

### Portals

By default, core appends `editor.portalElement` to the contenteditable's parent, which is the `.bn-container`. React gives that portal element the same theme class and `data-color-scheme`, so the current variable bridge applies independently of inheritance. Custom `portalElements` targets need separate review: UI rendered directly into an arbitrary external target may not inherit an editor container's app tokens, and the ShadCN setup documentation warns that replacement ShadCN components should not create their own portals. Hakgyo does not currently pass `portalElements` or replacement `shadCNComponents` in its two editor wrappers.

### Block and inline colors

Core defaults both block `textColor` and `backgroundColor` to the string `"default"`. For that value, the renderer emits no `data-text-color` or `data-background-color` attribute, so normal content inherits `.bn-editor`. A named or arbitrary non-default value emits an attribute and overrides the inherited editor color through BlockNote's color rules. Inline styled text follows the same principle. Thus changing only the two editor variables cannot recolor content whose saved data explicitly selects a text or background color.

Core's base `Block.css` includes hardcoded fallback rules for named colors, but React's later theme stylesheet repeats those selectors using `--bn-colors-highlights-*`. In the distributed ShadCN stylesheet, the variable-based rules come later and win at equal specificity. This is separate from the editor surface bridge.

### Why the previous regression test was insufficient

`apps/web/src/styles/blocknote-theme.test.ts` only checks that declaration strings are present in `globals.css`. It does not render BlockNote, verify the root classes, load both CSS chunks, or assert `getComputedStyle()` for `.bn-editor`. It protected against accidentally deleting the mapping, but it could not prove selector matching, cascade behavior, or visible contrast.

### Recommended integration after this research

1. Keep the `theme="light" | "dark"` prop; in the ShadCN wrapper it selects the scheme but does not provide a custom theme object.
2. Keep the CSS-variable bridge on the BlockNote root. For a more application-owned scope, pass a custom class to `BlockNoteView` and target `.bn-root.hakgyo-blocknote[data-color-scheme]`; unlike an arbitrary `data-*` prop, `className` is copied to both the visible root and BlockNote's portal root in 0.53.0.
3. Do not try to solve the screenshot by increasing selector specificity again. Introduce a visibly distinct editor-surface token or increase the derived card/background separation if visual hierarchy is desired.
4. Add a browser-level computed-style test that verifies the resolved `--bn-colors-editor-*`, `background-color`, and `color`, rather than only searching CSS source text.
5. Continue treating custom blocks separately: their direct Tailwind/app-token styles are not controlled by BlockNote's editor foreground variable.

## 1. What `@blocknote/shadcn` inherits from the application

The official setup says `@blocknote/shadcn` is intended for applications already using shadcn and Tailwind. It does not supply the host shadcn theme itself. The consuming stylesheet must include Tailwind, scan the package with `@source`, define the `dark` variant, provide shadcn CSS variables, and add the BlockNote border base rule. [Official ShadCN setup](https://www.blocknotejs.org/docs/getting-started/shadcn)

The first-party source confirms that BlockNote's ShadCN components use semantic utility classes rather than a separate BlockNote palette. Examples include:

- toolbars and suggestion menus: `bg-popover`, `text-popover-foreground`, `border`, and `shadow-md`;
- menu items: `focus:bg-accent`, `focus:text-accent-foreground`, and `text-destructive`;
- buttons: `bg-primary`, `text-primary-foreground`, `bg-background`, `bg-muted`, `border-border`, `ring-ring`, and `shadow-xs`;
- cards: `bg-card`, `text-card-foreground`, and `shadow-xs`;
- inputs: `border-input`, `text-foreground`, `placeholder:text-muted-foreground`, and focus/error ring tokens.

See the v0.53.0 first-party implementations for [Toolbar](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/shadcn/src/toolbar/Toolbar.tsx), [Button](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/shadcn/src/components/ui/button.tsx), [Dropdown Menu](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/shadcn/src/components/ui/dropdown-menu.tsx), [Card](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/shadcn/src/components/ui/card.tsx), and [Input](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/shadcn/src/components/ui/input.tsx).

Consequences for Hakgyo:

- `--card` matters for BlockNote cards, but not for the main editable surface by itself.
- `--popover` controls BlockNote dropdowns, slash menus, floating panels, and toolbar surfaces.
- the app's `--primary`, `--accent`, `--muted`, `--destructive`, `--border`, `--input`, and `--ring` values already cover most interactive editor UI;
- the organization shadow scale reaches the ShadCN BlockNote components because they use `shadow-xs`, `shadow-md`, and related Tailwind utilities;
- `.bn-shadcn * { @apply border-border outline-ring/50; }`, which already exists in Hakgyo, is part of the official integration pattern.

## 2. BlockNote's separate `--bn-*` theme variables

BlockNote documents the following public CSS-variable surface. These variables belong on `.bn-root[data-color-scheme]`; mode-specific overrides can target `data-color-scheme="light"` and `data-color-scheme="dark"`. [Official themes documentation](https://www.blocknotejs.org/docs/react/styling-theming/themes)

| Group | Variables | Purpose |
| --- | --- | --- |
| Editor | `--bn-colors-editor-text`, `--bn-colors-editor-background` | Default document foreground and main `.bn-editor` surface |
| Menu | `--bn-colors-menu-text`, `--bn-colors-menu-background` | Generic menu text/surface fallbacks |
| Tooltip | `--bn-colors-tooltip-text`, `--bn-colors-tooltip-background` | Tooltip foreground/surface |
| Hover | `--bn-colors-hovered-text`, `--bn-colors-hovered-background` | Hovered controls/items |
| Selection | `--bn-colors-selected-text`, `--bn-colors-selected-background` | Selected controls/items |
| Disabled | `--bn-colors-disabled-text`, `--bn-colors-disabled-background` | Disabled states |
| Structure | `--bn-colors-shadow`, `--bn-colors-border`, `--bn-colors-side-menu` | Shadow color, borders, side-menu handles/guides |
| Shape/type | `--bn-border-radius`, `--bn-font-family` | BlockNote radius base and font stack |
| Content colors | `--bn-colors-highlights-{gray,brown,red,orange,yellow,green,blue,purple,pink}-{text,background}` | Named text and highlight colors stored in document content |

The first-party stylesheet derives additional internal values from these public inputs, including medium/light shadows, a border shorthand, and small/medium/large radius variants. The main editor applies the editor background, editor text, font family, and radius variables. [First-party React theme CSS at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/styles.css)

`--bn-colors-shadow` is a **color**, not a complete `box-shadow` value. Therefore it can be derived from Hakgyo's foreground color with transparency, but Hakgyo's full `x/y/blur/spread` shadow shape cannot be passed through this documented variable. The ShadCN UI around the document still uses Hakgyo's complete Tailwind shadow scale. Overriding BlockNote's internal `--bn-shadow-medium` or `--bn-shadow-light` could carry the full shape, but those are derived implementation details rather than the documented public contract and are consequently more upgrade-sensitive. [Official variable list](https://www.blocknotejs.org/docs/react/styling-theming/themes) and [first-party derivation at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/styles.css)

## 3. Light/dark behavior and the `theme` prop

Without an explicit `theme`, `BlockNoteView` follows an enclosing BlockNote context when present, otherwise the user's system color preference. Passing `theme="light"` or `theme="dark"` forces the scheme. The view then writes `data-color-scheme` and the matching class to the root and portal element, which is important because floating menus are rendered through that portal. [Official forcing-light/dark documentation](https://www.blocknotejs.org/docs/react/styling-theming/themes#forcing-lightdark-mode) and [first-party `BlockNoteView` source at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/BlockNoteView.tsx)

For `@blocknote/shadcn` 0.53.0, the React-level `theme` prop is typed as only `"light" | "dark"`. The richer programmatic `Theme` and `{ light, dark }` objects shown on the themes page are explicitly additional Mantine functionality, not the ShadCN API. For ShadCN, use the string prop to synchronize mode and CSS variables to customize values. [Official themes documentation](https://www.blocknotejs.org/docs/react/styling-theming/themes) and [first-party prop type at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/BlockNoteView.tsx)

Hakgyo already passes an explicit `theme` to both the authoring `BlockNoteView` and the learner read-only `BlockNoteView`. That is the right mode-control mechanism. The base variable mapping is now present; the remaining design question is whether the editor should share `--card` with its wrapper or use a more visibly distinct derived surface.

## 4. Default text and background colors are document data

BlockNote's default schema exposes color in two places:

- blocks have `backgroundColor` and `textColor` props, both defaulting to the string `"default"`; a block background also applies to nested blocks;
- styled inline text has `textColor` and `backgroundColor`, also defaulting to `"default"`.

[Official built-in block properties](https://www.blocknotejs.org/docs/features/blocks#default-block-properties) and [official inline style model](https://www.blocknotejs.org/docs/features/blocks/inline-content#default-styles)

`"default"` produces no named-color override, so the content inherits the editor foreground/background. Named values are represented in rendered DOM with attributes such as `data-text-color="red"`, `data-background-color="yellow"`, or inline-style equivalents. The React stylesheet maps those attributes to `--bn-colors-highlights-*-text` and `--bn-colors-highlights-*-background`; this is what allows one stored name to render differently in light and dark schemes. [First-party default props source at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/blocks/defaultProps.ts) and [first-party React theme CSS at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/editor/styles.css)

This separation is important:

```text
saved document value: "red"
               -> data-text-color="red"
               -> --bn-colors-highlights-red-text
               -> current light/dark rendered color
```

Changing an organization's theme variables therefore changes rendering without rewriting saved BlockNote JSON.

### Built-in color picker

The stock picker has a fixed list of ten choices: `default`, `gray`, `brown`, `red`, `orange`, `yellow`, `green`, `blue`, `purple`, and `pink`. It can show text and background sections. The formatting-toolbar button calls `editor.addStyles` for a named color and `editor.removeStyles` for `default`. [First-party `ColorPicker` source at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/components/ColorPicker/ColorPicker.tsx) and [first-party `ColorStyleButton` source at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/components/FormattingToolbar/DefaultButtons/ColorStyleButton.tsx)

The editor API also exposes `addStyles`, `removeStyles`, and `toggleStyles` with `textColor` and `backgroundColor`. [Official content manipulation API](https://www.blocknotejs.org/docs/reference/editor/manipulating-content#adding-styles)

The schema types these values as strings, and the external-HTML serializer treats a non-built-in string as a raw CSS color. However, the stock picker only emits the ten names above and the stock in-editor stylesheet only defines selectors for its nine named hues. Arbitrary in-editor color values should therefore be treated as a custom UI/CSS-extension concern rather than assumed to be covered by the default picker. [First-party default style serialization at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/blocks/defaultBlocks.ts), [first-party default props serialization at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/blocks/defaultProps.ts), and [first-party picker source at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/react/src/components/ColorPicker/ColorPicker.tsx)

### Export caveat

BlockNote's external-HTML serializer resolves built-in names through its static `COLORS_DEFAULT` light palette, while live editor rendering resolves names through CSS variables. A customized organization palette can therefore render correctly inside BlockNote but export built-in names to the library's static default colors unless Hakgyo adds a separate export transformation. [First-party default color constants at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/editor/defaultColors.ts), [default inline-style serializer at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/blocks/defaultBlocks.ts), and [default block-prop serializer at v0.53.0](https://github.com/TypeCellOS/BlockNote/blob/v0.53.0/packages/core/src/blocks/defaultProps.ts)

## 5. Custom block styling

`createReactBlockSpec` renders an application-owned React component. Its `propSchema` defines saved block properties, while `render` controls the DOM and can attach classes, inline variables, and `data-*` attributes. [Official custom blocks documentation](https://www.blocknotejs.org/docs/features/custom-schemas/custom-blocks)

BlockNote's supported CSS hooks include `.bn-root`, `.bn-container`, `.bn-editor`, `.bn-block`, `.bn-block-content`, `.bn-inline-content`, toolbar/menu classes, `[data-content-type="..."]`, and data attributes generated from non-default block props. [Official overriding-CSS reference](https://www.blocknotejs.org/docs/react/styling-theming/overriding-css)

For Hakgyo custom blocks, prefer application semantic tokens directly inside the React render output:

- surfaces: `bg-card`, `bg-muted`, `bg-accent`, or `var(--card)`;
- text: `text-foreground`, `text-muted-foreground`, or the paired foreground token for the chosen surface;
- structure: `border-border`, `ring-ring`, `rounded-*`, and `shadow-*`;
- intentional semantic states: `destructive` or dedicated success/warning/info tokens if the app introduces them.

Custom blocks do **not** automatically inherit BlockNote's named color behavior merely because they are rendered inside `.bn-root`. To opt a custom rich-text block into BlockNote's block-level text/background props, include the relevant `defaultProps` entries in its `propSchema` and let the corresponding attributes reach the block DOM. Otherwise its custom DOM styling remains the application's responsibility. The official alert example demonstrates both patterns: it includes `defaultProps.textColor`, but styles the alert's own tone surface and icon through custom DOM/CSS. [Official custom block example](https://www.blocknotejs.org/docs/features/custom-schemas/custom-blocks)

## 6. Audited Hakgyo bridge

The following reflects the integration now present in Hakgyo. Scope it to `.bn-root` so BlockNote receives the application tokens without changing the meaning of those tokens globally:

```css
.bn-root[data-color-scheme] {
  --bn-colors-editor-text: var(--card-foreground);
  --bn-colors-editor-background: var(--card);

  --bn-colors-menu-text: var(--popover-foreground);
  --bn-colors-menu-background: var(--popover);
  --bn-colors-tooltip-text: var(--popover-foreground);
  --bn-colors-tooltip-background: var(--popover);

  --bn-colors-hovered-text: var(--accent-foreground);
  --bn-colors-hovered-background: var(--accent);
  --bn-colors-selected-text: var(--primary-foreground);
  --bn-colors-selected-background: var(--primary);
  --bn-colors-disabled-text: var(--muted-foreground);
  --bn-colors-disabled-background: var(--muted);

  --bn-colors-border: var(--border);
  --bn-colors-side-menu: var(--muted-foreground);
  --bn-colors-shadow: color-mix(in oklch, var(--foreground) 20%, transparent);
  --bn-border-radius: var(--radius);
  --bn-font-family: var(--app-font-family);
}
```

Why map editor background to `--card`:

- the editor is an elevated content surface within a page, so `card` preserves hierarchy against `background`;
- it fixes the gap where ShadCN BlockNote cards use `--card` but `.bn-editor` still uses BlockNote's static white/dark defaults;
- learner rendering can deliberately keep `.bn-editor { background: transparent; }` when the surrounding course surface should remain visible. That existing learner override is a product-level exception, not evidence that the editor variable is unnecessary.

### Highlight palette recommendation

Define all 18 `--bn-colors-highlights-*` variables for both modes. Preserve the meaning of each saved hue instead of mapping every hue to the organization primary color. A safe theme engine should derive accessible text/background pairs for gray, brown, red, orange, yellow, green, blue, purple, and pink, then expose them under BlockNote's expected names.

Two implementation strategies are valid:

1. Generate dedicated app-level semantic pairs such as `--editor-red-text` / `--editor-red-background`, then alias BlockNote variables to them. This is the clearest long-term contract.
2. Derive the BlockNote variables directly from existing theme colors using `color-mix()`. This requires fewer app tokens but needs careful contrast tests, especially for yellow, orange, and dark mode.

Do not use `--primary` for all named highlights: a document author choosing “red” or “green” is storing semantic color intent, and collapsing those names to one brand color would erase that distinction.

Use selectors keyed by BlockNote's own mode attribute if the app stores explicit light and dark pairs:

```css
.bn-root[data-color-scheme="light"] {
  --bn-colors-highlights-red-text: var(--editor-red-text-light);
  --bn-colors-highlights-red-background: var(--editor-red-background-light);
  /* repeat for the other named hues */
}

.bn-root[data-color-scheme="dark"] {
  --bn-colors-highlights-red-text: var(--editor-red-text-dark);
  --bn-colors-highlights-red-background: var(--editor-red-background-dark);
  /* repeat for the other named hues */
}
```

Using `data-color-scheme` keeps content colors synchronized with the explicit `BlockNoteView theme` prop, including portal-rendered UI, rather than assuming the outer document's `.dark` class is always the sole source of truth.

## 7. Repo-specific follow-up checklist

No application code was changed as part of this research. A later implementation should:

1. Decide whether authoring `.bn-editor` should share `--card` with its surrounding section. If it needs to read as a separate canvas, derive a dedicated editor-surface pair with a perceptible contrast delta.
2. Add light/dark named highlight pairs and contrast tests for every text/background pair.
3. Keep passing the explicit `"light" | "dark"` value to both authoring and learner `BlockNoteView` instances.
4. Replace or supplement the source-string regression test with a rendered computed-style test.
5. Verify normal editor content, read-only learner content, toolbar, slash menu, color picker, selected/hovered/disabled controls, block-level colors, inline colors, nested colored blocks, and portal-rendered dropdowns in both modes.
6. Audit custom blocks separately. Fixed Tailwind hue utilities may be intentional semantic colors, but they do not become controlled by BlockNote's variables simply because the base editor variables are mapped.
7. If themed HTML export is needed, add an explicit export-color policy because BlockNote's stock external serializer uses static default light colors.
8. Treat selectors and variables not listed in the official themes documentation as upgrade-sensitive, and re-check first-party source when upgrading from 0.53.0.
